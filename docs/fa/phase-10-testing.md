# فاز ۱۰ — تست و دیباگ (Testing & Debugging)

- **وضعیت:** کامل شد، ۲۰۲۶-۱۱-۲۴. همهٔ بررسی‌ها سبز است.
- **هدف فاز:** مطمئن شویم سایت با یک مرورگر واقعی — نه فقط با تست واحد — کار می‌کند: کاربر وارد می‌شود، طعم عوض می‌کند، به سبد اضافه می‌کند، سفارش می‌دهد و فرم‌ها را پر می‌کند؛ و ظاهر صفحه در پنج عرض مختلف با نسخهٔ قبلی فرقی نکرده است.

## ۱. تست E2E چیست و چرا لازم است؟

تا فاز ۹ فقط **تست واحد** داشتیم (Vitest): هر قطعهٔ کوچک — مثلاً یک تابع یا یک کامپوننت — جدا از بقیه تست می‌شد. تست واحد نمی‌گوید «وقتی کاربر واقعی روی دکمه می‌زند چه می‌شود؟». **تست E2E** (مخفف End-to-End، یعنی سرتاسری) دقیقاً همان کار را می‌کند: یک مرورگر واقعی (فایرفاکس) باز می‌شود، صفحهٔ واقعی لود می‌شود، روی دکمه‌های واقعی کلیک می‌شود و نتیجهٔ واقعی دیده می‌شود. اگر چرخ طعم خراب شود، فرم سفارش خطا بدهد یا سبد خالی نشود، این تست‌ها قرمز می‌شوند — قبل از اینکه مشتری ببیند.

ابزار این کار **Playwright** است (نسخهٔ ۱٫۶۵٫۱). تست‌ها با `pnpm test:e2e` اجرا می‌شوند.

## ۲. چه چیزی تست می‌شود؟ (۵۸ تست)

همهٔ تست‌ها در هر دو زبان (`/fa` و `/en`) اجرا می‌شوند و به‌جای سلکتورهای شکنندهٔ CSS از نقش‌های دسترس‌پذیر (دکمه با نام مشخص، دیالوگ با عنوان) استفاده می‌کنند:

| فایل | چه چیزی | تعداد |
| --- | --- | --- |

**نکتهٔ مهم دربارهٔ جمع سفارش:** تست تسویهٔ حساب عمداً چک می‌کند که جمعِ نمایش‌داده‌شده همان جمعی است که **سرور** حساب کرده (۱۸۰٬۰۰۰ تومان برای یک کورو اورجینال). مرورگر هیچ جمعی نمی‌فرستد؛ اگر کسی جمع را دستکاری کند، سرور باز هم قیمت درست را برمی‌گرداند (فاز ۶).

**نکتهٔ مهم دربارهٔ پرداخت:** در حالت آزمایشی (Mock) پرداخت بلافاصله «پرداخت شده» می‌شود — پول واقعی جابه‌جا نمی‌شود. تست هم همین را چک می‌کند.

**نکتهٔ مهم دربارهٔ صفحهٔ ۴۰۴:** آدرس‌های ناشناخته صفحهٔ `global-not-found.tsx` را نشان می‌دهند که عمداً فارسی-اول است (چون از همهٔ layoutها می‌گذرد و next-intl در آنجا در دسترس نیست) و پاراگراف انگلیسی را هم داخل خودش دارد. پس `/en/does-not-exist` هم همان صفحهٔ فارسی را نشان می‌دهد — این باگ نیست، طراحی است.

## ۳. رگرسیون تصویری یعنی چه؟

یعنی «عکس صفحه را با عکس دفعهٔ قبل مقایسه کن». برای هر زبان و هر عرض (۳۶۰، ۷۶۸، ۱۰۲۴، ۱۴۴۰، ۱۹۲۰ پیکسل) دو عکس گرفته می‌شود: یکی از هیرو (بالای صفحه) و یکی از کل صفحه. این ۲۰ عکس در `apps/web/tests/visual/baseline/` کامیت شده‌اند. هر بار که تست اجرا شود، عکس تازه با عکس پایه مقایسه می‌شود؛ اگر بیش از ۲٪ پیکسل‌ها فرق کنند، تست قرمز می‌شود. پس اگر یک تغییر CSS چیدمان را بشکند، قبل از دیپلوی لو می‌رود.

برای اینکه عکس‌ها قطعی باشند (هر بار دقیقاً یکی شوند):

- انیمیشن‌ها خاموش می‌شوند (`prefers-reduced-motion` + غیرفعال کردن انیمیشن در لحظهٔ عکس).
- صفحه یک بار تا ته اسکرول می‌شود تا همهٔ بخش‌ها ظاهر شوند، بعد برمی‌گردد بالا. **اسکرول عمداً آهسته است (۳۰۰ پیکسل در هر ۲۵۰ میلی‌ثانیه):** اسکرول سریع از جلوی مکانیزم lazy-load فایرفاکس رد می‌شود و عکس‌های زیر صفحه هرگز شروع به لود نمی‌کنند — در فاز ۱۰ همین باعث شد ردیف دوم کارت‌های منو در عکس کامل سیاه بیفتد و تست تصویری در ۱۴۴۰ و ۱۹۲۰ پیکسل تایم‌اوت بخورد (بخش ۶، ردیف ۹).
- بعد از اسکرول، تست صبر می‌کند تا **همهٔ عکس‌ها کامل لود شوند** (`img.complete` با مهلت ۶۰ ثانیه) و بعد شبکه آرام شود؛ فقط آن‌وقت عکس گرفته می‌شود.
- عکس صفحهٔ کامل، باند خالیِ بخش هیرو (۳۰۰vh) را هم دارد — چون هیروی چسبان فقط در اولین ویوپورت است و بقیهٔ آن بخش خالی است. این باند جزئی از عکس پایه است، نه عیب.

**بازتولید عکس‌های پایه** — فقط وقتی ظاهر را عمداً عوض کردی (مثلاً رنگ یا چیدمان جدید):

```bash
cd ~/workspace/ela-coffee
pnpm --filter web exec playwright test --project=visual --update-snapshots
```

**قبل از کامیت، تفاوت عکس‌های تازه را با چشم ببین** — بازتولید بی‌فکر، خطای بصری را در پایه دفن می‌کند.

⚠️ **نکتهٔ مهم دربارهٔ `--update-snapshots`:** حالت پیش‌فرض آن فقط عکس‌هایی را بازنویسی می‌کند که **تستشان قرمز شده** باشد. در فاز ۱۰ بعد از درست‌شدن کنتراست کارت‌های منو، تست تصویری سبز ماند — چون تفاوت پیکسلی (حدود ۲٫۵٪ به معیار خام، ولی کمتر از ۲٪ به معیار pixelmatch که تفاوت‌های تیره‌روی‌تیره را نادیده می‌گیرد) زیر آستانه بود — و عکس‌های پایهٔ **قدیمی و غلط** سر جایشان ماندند. راه درست این بود: عکس‌های پایه حذف و از اول ساخته شوند (`rm tests/visual/baseline/*.png` و بعد همان دستور بالا)، و عکس‌های تازه با چشم بررسی شوند. «تست سبز شد» به‌تنهایی ثابت نمی‌کند عکس پایه درست است.

## ۴. چطور تست‌ها را اجرا کنیم؟

```bash
cd ~/workspace/ela-coffee

# همهٔ تست‌های E2E (هر دو پروژه: کارکردی + تصویری) — خودش بیلد پروداکشن می‌گیرد و سرور را بالا می‌آورد
pnpm --filter web test:e2e

# فقط تست‌های کارکردی (بدون تصویری)
pnpm --filter web exec playwright test --project=e2e

# فقط تصویری
pnpm --filter web exec playwright test --project=visual

# یک فایل مشخص
pnpm --filter web exec playwright test --project=e2e hero.spec.ts

# با مرورگر قابل‌مشاهده (headed) برای دیباگ
pnpm --filter web exec playwright test --project=e2e --headed

# حالت تعاملی (UI mode) — بهترین ابزار دیباگ: قدم‌به‌قدم، با اسکرین‌شات و لاگ
pnpm --filter web exec playwright test --ui
```

**نکتهٔ سرعت:** اولین اجرا بیلد پروداکشن می‌گیرد (حدود یک دقیقه) و بعد هر تست صفحه را در فایرفاکس لود می‌کند؛ کل سوئیت حدود ۱۰ دقیقه طول می‌کشد. اگر سرور پروداکشن روی پورت ۳۰۰۰ از قبل بالا باشد، همان سرور استفاده می‌شود و بیلد تکرار نمی‌شود.

**چرا فایرفاکس و نه کروم؟** در این محیط دانلود کرومیوم مسدود است و فایرفاکسِ کش‌شده (نسخهٔ ۱۵۷۲) با Playwright ۱٫۶۵٫۱ کار می‌کند. در CI (گیت‌هاب) کروم هست، پس پروژهٔ کارکردی آنجا روی کرومیوم اجرا می‌شود (`E2E_BROWSER=chromium`)؛ پروژهٔ تصویری همه‌جا فایرفاکس است تا عکس‌های پایه قابل‌مقایسه بمانند.

## ۵. خواندن یک تست خراب

وقتی تستی قرمز می‌شود، Playwright سه چیز می‌سازد:

1. **اسکرین‌شات** لحظهٔ خطا: `apps/web/test-results/<نام تست>/test-failed-1.png`
2. **‏error-context.md**: متن خطا + تصویر متنیِ صفحه در لحظهٔ خطا (کدام دکمه‌ها و متن‌ها بودند)
3. **‏trace** (فقط وقتی تست در CI یک بار retry شود): با `pnpm --filter web exec playwright show-trace <فایل trace.zip>` باز می‌شود و هر قدم را مثل فیلم نشان می‌دهد.

قاعدهٔ طلایی: **اول متن خطا را بخوان، بعد حدس بزن.** بیشتر خطاها یکی از این سه‌تا هستند:

- **‏strict mode violation (دو عنصر پیدا شد):** سلکتور به‌جای یک عنصر، دو تا پیدا کرده. راه‌حل: سلکتور را دقیق‌تر کن (`exact: true` یا محدودهٔ کوچک‌تر مثل داخل دیالوگ). این دقیقاً همان چیزی بود که در اولین اجرای فاز ۱۰ پیش آمد (دکمهٔ «قهوه» با نقطهٔ چرخ «دارچین و شکر قهوه‌ای» قاطی شد).
- **‏Timeout (عنصر پیدا نشد):** یا صفحه هنوز لود نشده (صبر کن — Playwright خودش تا ۱۰ ثانیه صبر می‌کند) یا واقعاً عنصر نیست — یعنی باگ واقعی در اپ.
- **‏Page crashed:** صفحه در مرورگر کرش کرده. در فاز ۱۰ این دقیقاً برای axe-core ۴٫۱۴٫۱ با دیالوگ باز پیش آمد — ربطی به اپ نداشت (بخش ۶).

**هرگز** برای سبز شدن تست، assertion را ضعیف نکن و sleep طولانیِ دستی نگذار؛ به‌جایش از `expect.poll` یا `waitFor` استفاده کن.

**چرا فاز ۹ این کنتراست‌ها را نگرفته بود؟** معلوم نیست — کنتراست کارت منو و eyebrow قطعی است و به زمان‌بندی ربط ندارد. فاز ۹ در آن زمان axe را در ۸ حالت صفر خطا گزارش کرده بود (با وضعیت color-contrast به‌صورت «ناتمام»). این‌جا صادقانه ثبت می‌شود: سوئیت E2E فاز ۱۰ بود که این دو باگ را پیدا کرد؛ ادعای فاز ۹ بدون سند، غلط خوانده نمی‌شود.

## ۷. CI بعد از فاز ۱۱ چه می‌کند؟

در `.github/workflows/ci.yml` یک جاب جدید `e2e` هست: وابستگی‌ها نصب می‌شوند، مرورگرهای Playwright (کرومیوم + فایرفاکس) نصب می‌شوند و `pnpm --filter web test:e2e` اجرا می‌شود. **این جاب هنوز در هیچ CI واقعی اجرا نشده** — چون ریپو هنوز روی گیت‌هاب نیست. اولین اجرای واقعی با push در فاز ۱۱ اتفاق می‌افتد؛ تا آن موقع، «CI سبز است» ادعا نشده.

## ۸. دستورهای این فاز

```bash
cd ~/workspace/ela-coffee
pnpm install --frozen-lockfile
pnpm typecheck && pnpm lint && pnpm test && pnpm build
pnpm --filter web test:e2e        # سوئیت کامل E2E + تصویری
```

## ۹. کارهای باز (از فازهای قبل، بدون تغییر)

Neon و `DATABASE_URL`، شناسهٔ sandbox زرین‌پال، اطلاعات تماس واقعی، بازبینی ۳۲ ترجمهٔ `TODO(review)`، مدرک لایسنس، قیمت‌های واقعی به‌جای قیمت‌های جای‌نگهدار.
