# فاز ۷ — امنیت (Security Hardening)

- **وضعیت:** انجام شد (۲۰۲۶-۱۱-۲۴)؛ فاز ۶ تایید شده بود و فاز ۷ با دستور تو شروع شد.
- **هدف این فاز:** قفل‌کردن درهایی که یک فروشگاه آنلاین باید قفل باشند — هدرهای امنیتی، جلوگیری از درخواست جعلی از سایت دیگر، اعتبارسنجی ورودی‌ها، محدودیت سرعت و تلهٔ ربات‌ها — بدون اینکه چیزی از کار بیفتد. نسخهٔ کامل و انگلیسی این مستند در `SECURITY.md` ریشهٔ ریپو است؛ این سند همان‌ها را به زبان ساده توضیح می‌دهد.

> اگر فقط می‌خواهی بررسی کنی، برو سراغ بخش «اجرا و بررسی» در پایین.

---

## ۱. هدرهای امنیتی — مرورگر چه چیزهایی را اجازه می‌دهد؟

وقتی سرور جواب می‌دهد، چند هدر می‌فرستد که به مرورگر می‌گویند «این صفحه چه کارهایی می‌تواند بکند». همه در `apps/web/next.config.ts` تنظیم شده‌اند و روی **همهٔ مسیرها** (صفحه‌ها و API) اعمال می‌شوند:

| هدر                               | یعنی چه، به زبان ساده                                                                                                                        |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `Content-Security-Policy`         | «فقط از خودمان بارگذاری کن.» هیچ اسکریپت، فونت، عکس یا فریمی از سایت دیگری اجازه ندارد. اگر مهاجمی کد مخرب تزریق کند، مرورگر اجرایش نمی‌کند. |
| `Strict-Transport-Security`       | «فقط با HTTPS بیا.» مرورگر بعد از اولین بازدید، دیگر نسخهٔ http را باز نمی‌کند.                                                               |
| `X-Content-Type-Options: nosniff` | مرورگر حدس نمی‌زند فایل چیست؛ اگر فایلی `text/html` نیست، آن را صفحه حساب نمی‌کند.                                                           |
| `Referrer-Policy`                 | وقتی کاربر روی لینک خروجی می‌زند، آدرس کامل صفحه فاش نمی‌شود.                                                                                |
| `Permissions-Policy`              | دوربین، میکروفون، موقعیت و پرداخت مرورگر برای این سایت خاموش‌اند — فروشگاه به هیچ‌کدام نیاز ندارد.                                           |
| `X-Frame-Options: DENY`           | هیچ سایتی نمی‌تواند صفحهٔ ما را داخل iframe بگذارد (جلوگیری از clickjacking).                                                                 |

### چرا CSP دو تا `'unsafe-inline'` دارد؟ — تصمیم صادقانهٔ این فاز

این مهم‌ترین تصمیم فاز ۷ است و باید بدانی چرا:

سیاست سخت‌گیرانهٔ CSP با **nonce** (یک کد یک‌بارمصرف برای هر درخواست) در مستندات خود Next.js آمده است. ولی همان مستندات می‌گویند nonce به **رندر داینامیک** نیاز دارد و «Partial Prerendering با nonce ناسازگار است» — و پروژهٔ ما دقیقاً برای سرعت، PPR و `cacheComponents` را روشن کرده است. پس دو راه بود: یا PPR را خاموش کنیم و سرعت را بدهیم، یا CSP استاتیک با دو استثنای مستند بگذاریم. راه دوم انتخاب شد:

- `script-src 'unsafe-inline'` — چون Next.js برای راه‌اندازی صفحه اسکریپت‌های inline می‌سازد که روی صفحات استاتیک نمی‌توانند nonce داشته باشند.
- `style-src 'unsafe-inline'` — چون چرخ طعم با `style` inline متغیرهای `--rot` و `--pour` را می‌چرخاند؛ CSP به استایل inline هم nonce نمی‌تواند بدهد. استایل inline نمی‌تواند کد اجرا کند، پس خطرش کم است.

جبرانش چیست؟ `default-src 'self'` یعنی **هیچ‌چیز** از بیرون نمی‌آید (نه فونت گوگل، نه CDN، نه اسکریپت ثالث)، `object-src 'none'` و `base-uri 'self'` هم بسته‌اند. اگر روزی امنیت سخت‌گیرانه‌تر لازم شد، معامله‌اش روشن است: PPR خاموش شود و CSP با nonce به `proxy.ts` برود.

یک نکتهٔ دیگر: در حالت توسعه (`dev`) عبارت `'unsafe-eval'` هم به اسکریپت‌ها اضافه می‌شود، چون React برای دیباگ از `eval` استفاده می‌کند؛ در پروداکشن این عبارت **نیست**.

## ۲. CSRF — درخواست جعلی از سایت دیگر

فرض کن کاربر در سایت مخربی است و آن سایت با جاوااسکریپت به `/api/orders` ما POST می‌زند تا با هویت کاربر سفارش بسازد. مرورگر کوکی نمی‌فرستد (کوکی نداریم)، ولی حمله هنوز ممکن بود. راه‌حل (`apps/web/src/lib/csrf.ts`):

- هر POST اول چک می‌کند هدر `Origin` (یا اگر نبود، `Referer`) با آدرس خودمان یکی باشد.
- اگر Origin مال سایت دیگری بود → **۴۰۳**.
- اگر اصلاً Origin و Referer نبود → **۴۰۳**. مرورگر روی POST همیشه Origin می‌فرستد، پس نبودنش یعنی مشتری مرورگر نیست و مشتری غیرمرورگر هم برای این API پشتیبانی نمی‌شود.

**CORS** هم همین‌جا بسته شد: هیچ `*`ای نیست. هدر `Access-Control-Allow-Origin` فقط وقتی برگردانده می‌شود که Origin دقیقاً مال خودمان باشد. یعنی هیچ سایت دیگری نمی‌تواند از API ما بخواند؛ API ما فقط مال خودمان است.

## ۳. ورودی‌ها — هیچ‌چیز بدون چک وارد نمی‌شود

- هر ۷ روت با Zod چک می‌شوند (همان اسکیماهایی که فرم‌های فرانت‌اند هم استفاده می‌کنند). نام ≤ ۱۰۰ کاراکتر، پیام ≤ ۲۰۰۰ کاراکتر، مهمان ۱ تا ۱۲، تعداد ۱ تا ۱۰.
- آیدی‌های رکورد (سفارش/رزرو) فقط می‌توانند حروف، عدد، `-` و `_` باشند؛ آیدی بدشکل ۴۰۰ می‌گیرد و آیدی ناشناختهٔ خوش‌شکل ۴۰۴.
- **بهداشت متن:** در نام و پیام، کاراکترهای `<` و `>` در مرز اعتبارسنجی حذف می‌شوند. React خودش هم هنگام رندر escape می‌کند و در کل کدبیس حتی یک `dangerouslySetInnerHTML` هم نیست (با grep بررسی شد). تستش این است: با نام `<script>alert(1)</script>Ali` سفارش ساخته شد، در API برگشت و در React به‌صورت **متن** دیده شد — هیچ تگ `<script>`ای ساخته نشد.
- **خطاها امن‌اند:** جواب خطا همیشه `{ error: { code, message } }` است؛ هیچ stack trace و هیچ خطای Prisma به بیرون نمی‌رسد. اگر چیزی غیرمنتظره خراب شد، جواب عمومی ۵۰۰ با کد `INTERNAL_ERROR` است.

## ۴. محدودیت سرعت و تلهٔ ربات‌ها

| اندپوینت       | محدودیت                        |
| -------------- | ------------------------------ |
| خبرنامه و تماس | ۵ درخواست در دقیقه برای هر IP  |
| سفارش و رزرو   | ۱۰ درخواست در دقیقه برای هر IP |

ربات که تند تند بزند، **۴۲۹** می‌گیرد با هدر `Retry-After` (چند ثانیه صبر کند). تست‌ها واقعاً ۱۱ درخواست پشت سر هم زده‌اند و ۴۲۹ را دیده‌اند.

**محدودیت صادقانه:** این محدودیت در حافظهٔ همان سرور زندگی می‌کند. روی Vercel هر نمونهٔ سرور حافظهٔ خودش را دارد، پس در برابر حملهٔ توزیع‌شدهٔ بزرگ کامل نیست. اگر روزی سوءاستفاده دیده شد، قدم بعدی یک فروشگاه خارجی (مثلاً Upstash) است — عمداً سرویسی نیست که در ایران بسته باشد.

**تلهٔ ربات (honeypot):** هر فرم یک فیلد نامرئی `website` دارد که انسان هیچ‌وقت نمی‌بیند. ربات آن را پر می‌کند؛ ما با جواب ۲۰۰ِ معمولی جواب می‌دهیم و **هیچ‌چیز ثبت نمی‌کنیم** — و ربات نمی‌فهمد لو رفته است. برای هر چهار فرم تست شده است.

## ۵. پرداخت و رازها

- اطلاعات کارت **هیچ‌وقت** به اپ ما نمی‌رسد؛ کاربر در صفحهٔ زرین‌پال پرداخت می‌کند و فقط یک کد authority برمی‌گردد.
- مبلغ همیشه سمت سرور از قیمت‌های دیتابیس حساب می‌شود؛ مجموع ارسالی مشتری نادیده گرفته می‌شود (فاز ۶، تست‌شده).
- **رازها:** فقط `.env.example` در گیت است و فقط جای‌خالی دارد. هیچ `.env.local`ای در ریپو نیست و `git log` هم هیچ رازی ندارد (با grep بررسی شد).
- **وابستگی‌ها:** `pnpm audit` در CI اضافه شد (روی high/critical خطا می‌دهد). یک نکته: در این محیط سندباکس، سیاست رجیستری جلوی اندپوینت audit را می‌گیرد (۴۰۳)، پس `pnpm audit` اینجا اجرا نشد؛ اولین نتیجهٔ واقعی از CI می‌آید. `npm audit` هم کاربرد ندارد چون `package-lock.json` نداریم (مونورپوی pnpm).

## ۶. کوکی — فقط یکی، و فقط زبان

اپ لاگین ندارد، ولی **یک کوکی** می‌سازد: `NEXT_LOCALE` با مقدار `fa` یا `en` که next-intl برای یادآوری زبان می‌گذارد. فقط زبان است — زبان در آدرس صفحه (`/fa`، `/en`) هم هست، پس کوکی فقط یک راهنماست، نه توکن نشست. مشخصاتش: `SameSite=Lax` و `Path=/`، و `Secure` فقط در پروداکشن (چون کوکی Secure روی HTTP معمولی در توسعهٔ محلی ذخیره نمی‌شود و همگام‌سازی زبان را خراب می‌کند). عمداً `HttpOnly` **نیست**، چون خود next-intl هنگام عوض‌شدن زبان با جاوااسکریپت آن را می‌نویسد و جاوااسکریپت نمی‌تواند کوکی HttpOnly بنویسد. اگر روزی کوکی نشست اضافه شد، حتماً باید `HttpOnly` و `Secure` و `SameSite` باشد.

سبد خرید فقط در `localStorage` مرورگر می‌ماند. پیامدش: اگر روزی XSSای پیدا شود، می‌تواند سبد را بخواند — به همین دلیل است که CSP و escape کردن متن در این فاز جدی گرفته شد.

## ۷. چه چیزی هنوز پوشش داده نشده (ریسک‌های باقی‌مانده)

1. **احراز هویت نداریم.** هر کس آیدی سفارش را بداند می‌تواند وضعیتش را بخواند؛ آیدی‌ها UUID هستند پس حدس‌زدن عملی نیست، ولی چک مالکیت هم نیست. برای نسخهٔ اول (خرید مهمان) قابل‌قبول است.
2. **محدودیت سرعت per-instance** است (بخش ۴).
3. **CSP دو `unsafe-inline` دارد** (بخش ۱) — معاملهٔ PPR.
4. **WAF و هشدار سوءاستفاده نداریم**؛ فقط پیش‌فرض‌های Vercel و همین محدودیت‌ها.
5. **callback زرین‌پال ساخته نشده** — در حالت زرین‌پال پرداخت PENDING می‌ماند (فاز ۶).
6. **فروشگاه حافظه‌ای بدون دیتابیس** — اگر در دیپلوی `DATABASE_URL` جا بیفتد، سفارش‌ها با ری‌استارت پاک می‌شوند. چک‌لیست دیپلوی باید تنظیم‌بودن `DATABASE_URL` را چک کند.
7. **audit وابستگی‌ها هنوز اجرا نشده** — اولین نتیجه از CI می‌آید؛ اگر قرمز شد، قبل از مرج باید رفع یا مستند شود.

## ۸. اجرا و بررسی

```bash
cd ~/workspace/ela-coffee

pnpm install --frozen-lockfile
pnpm typecheck          # تایپ‌چک در هر سه پکیج
pnpm lint               # ESLint
pnpm test               # تست‌ها (شامل ۱۹ تست امنیتی جدید)
pnpm build              # بیلد پروداکشن
pnpm audit --audit-level high   # در این سندباکس ۴۰۳ می‌دهد؛ در CI و روی ماشین تو کار می‌کند

# هدرها، روی بیلد پروداکشن:
pnpm --filter web start --port 3100 &
curl -sI http://localhost:3100/fa | grep -iE "content-security-policy|strict-transport"
curl -sI http://localhost:3100/api/menu | grep -iE "strict-transport|permissions-policy"

# CSRF: درخواست cross-origin باید ۴۰۳ بگیرد
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:3100/api/newsletter \
  -H "Origin: https://evil.example" -H "Content-Type: application/json" \
  -d '{"email":"a@example.com"}'   # انتظار: 403

# بهداشت رازها:
git ls-files | grep -i env          # فقط .env.example
git log --all -p | grep -iE "BEGIN .*PRIVATE KEY|AKIA[0-9A-Z]{16}"  # باید خروجی نداشته باشد
```

- callback زرین‌پال، پنل مدیریت، احراز هویت — فازهای بعد، اگر خواسته شوند.
