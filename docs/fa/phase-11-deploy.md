## ۱. باگی که قبل از اولین پوش پیدا شد: CI هرگز اجرا نمی‌شد

فایل `.github/workflows/ci.yml` برای رویداد `push` فقط شاخهٔ `main` را گوش
می‌داد:

```yaml
on:
  push:
    branches: [main]
```

اما همهٔ کامیت‌های این پروژه — از فاز ۲ تا حالا — روی شاخهٔ **`master`**
هستند. یعنی اگر همین‌طور پوش می‌کردیم، هیچ جابی اجرا نمی‌شد و فکر
می‌کردیم «CI سبز است»، در حالی که اصلاً اجرا نشده بود.

**اصلاح (فاز ۱۱):** `branches: [main]` به `branches: [master]` تغییر کرد،
با کامنتی در خود فایل که دلیلش را توضیح می‌دهد. جاب `pull_request` بدون
فیلتر شاخه است و دست نخورده.

درس: همیشه بعد از پوش اول، در تب Actions گیت‌هاب چک کن که ران واقعاً
شروع شده باشد؛ «سبز» با «اجرا نشده» فرق می‌کند.

قبل از هر پوشی، از ریشهٔ پروژه اجرا شد:

بود (همان اتفاق فاز ۶). با `npm install -g pnpm@10.34.9` دوباره نصب شد
— نسخه همان ۱۰٫۳۴٫۹ است.

## ۳. سه‌تکهٔ پازل چطور به هم وصل می‌شوند

```
گیت‌هاب (ela-coffee، عمومی)
   │ push به master
   ▼
GitHub Actions (.github/workflows/ci.yml)
   │ جاب check: typecheck / lint / test / build / pnpm audit
   │ جاب e2e: Playwright روی Chromium + Firefox
   ▼
ورسل (پروژهٔ ela-coffee-yi88)
   │ هر push → دیپلوی Preview؛ push به master → دیپلوی Production
   ▼
https://ela-coffee-yi88.vercel.app
```

- **گیت‌هاب** خانهٔ کد است؛ تاریخچهٔ کامیت‌ها و CI آنجاست.
- **GitHub Actions** نگهبان است؛ هر پوش را تست می‌کند و اگر قرمز شد،
  ورسل دیپلوی نمی‌کند (دیپلوی فقط از کامیت سبز انجام می‌شود — عادت کن
  قبل از مرج، سبز بودن Actions را ببینی).
- **ورسل** میزبان است؛ سایت را سرو می‌کند و برای هر PR یک آدرس Preview
  می‌سازد تا قبل از مرج، تغییر را زنده ببینی.

## ۴. قدم‌به‌قدم: ساخت ریپو و اولین پوش (انجام شد ۱۴۰۴/۹/۴)

> این بخش را الهه انجام داد (ریپوی قدیمی را خودش حذف کرد و ریپوی تازه
> با همان نام ساخته شد)؛ قدم‌ها به‌عنوان سابقه نگه داشته شده‌اند.

1. در مرورگر به [github.com/new](https://github.com/new) برو و وارد
   حساب `elaheabdali` شو.
2. نام ریپو: `ela-coffee` — **Public** (به انتخاب صریح الهه؛ بخش ۸ را
   ببین). تیک «Add a README» را **نزن** (ریپو از قبل README دارد؛ تیک زدن
   تاریخچه را به‌هم می‌ریزد).
3. Create repository را بزن. گیت‌هاب یک صفحهٔ خالی با دستورها نشان می‌دهد.
4. در ترمینال، از ریشهٔ پروژه:
   ```bash
   git remote add origin https://github.com/elaheabdali/ela-coffee.git
   git push -u origin master
   ```
   اگر مرورگر ازت خواست، با همان حساب گیت‌هاب وارد شو.
5. چک کن: `git ls-remote origin` باید کامیت `master` را نشان بدهد و در
   صفحهٔ ریپو، فایل‌ها دیده شوند.
6. همان پوش، اولین ران CI را شروع می‌کند — تب **Actions** را باز کن و
   صبر کن تا هر دو جاب (`check` و `e2e`) تمام شوند (بخش ۷).

راه جایگزین با `gh` CLI (اگر روزی خواستی از ترمینال انجامش بدهی):

```bash
gh auth login            # ورود تعاملی؛ یک کد نشان می‌دهد که در مرورگر وارد می‌کنی
gh repo create ela-coffee --private --source=. --remote=origin --push
```

## ۵. قدم‌به‌قدم: دیپلوی ورسل (انجام شد ۱۴۰۴/۹/۴ — آدرس واقعی: `ela-coffee-yi88.vercel.app`)

1. در مرورگر به [vercel.com/new](https://vercel.com/new) برو و وارد شو.
2. **Import Git Repository** را بزن و ریپوی `elaheabdali/ela-coffee` را
   انتخاب کن. (اگر ورسل به گیت‌هابت دسترسی ندارد، اول GitHub App ورسل
   را نصب کن — خودش راهنمایی‌ات می‌کند.)
3. تنظیمات پروژه — **مهم، چون مونورپو است:**
   | تنظیم            | مقدار                       |
   | ---------------- | --------------------------- |
   | Framework Preset | Next.js                     |
   | Root Directory   | `apps/web`                  |
   | Install Command  | `pnpm install`              |
   | Build Command    | `pnpm --filter web build`   |
   | Output Directory | (پیش‌فرض Next.js — دست نزن) |
   | Node.js Version  | 24.x                        |
4. در همان صفحه، **Environment Variables** را اضافه کن (جدول بخش ۶).
5. **Deploy** را بزن. اولین دیپلوی چند دقیقه طول می‌کشد (نصب + بیلد).
6. وقتی تمام شد، ورسل یک آدرس می‌دهد؛ آدرس واقعی این پروژه
   `https://ela-coffee-yi88.vercel.app` شد (ورسل نام پروژه را
   `ela-coffee-yi88` گذاشت، چون `ela-coffee` گرفته شده بود). همان آدرس
   واقعی در `NEXT_PUBLIC_SITE_URL` گذاشته شده (بخش ۶).

## ۶. جدول متغیرهای محیطی — چه چیزی ست شده، چه چیزی نه

در داشبورد ورسل، **Settings → Environment Variables**، برای هر سه محیط
(Production ،Preview ،Development) — مگر جایی که گفته شده:

| متغیر                  | مقدار در دیپلوی اول                                       | چرا                                                                                                                                                              |
| ---------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NEXT_PUBLIC_SITE_URL` | `https://ela-coffee-yi88.vercel.app` (آدرس واقعی ورسل) | جای‌نگهدارِ فاز ۸ را جایگزین می‌کند؛ canonical و hreflang و sitemap و OG از همین ساخته می‌شوند. اگر خالی بماند، کد به همان جای‌نگهدار برمی‌گردد — پس حتماً ست شود. |
| `PAYMENT_PROVIDER`     | **تنظیم نمی‌شود** (پیش‌فرض Mock)                          | پرداخت واقعی هنوز نمی‌خواهیم؛ Mock بدون شبکه و بدون پول واقعی کار می‌کند.                                                                                        |
| `ZARINPAL_MERCHANT_ID` | **تنظیم نمی‌شود** (خالی)                                  | فقط وقتی `PAYMENT_PROVIDER=zarinpal` باشد خوانده می‌شود؛ شناسهٔ sandbox را هنوز نداری.                                                                            |
| `DATABASE_URL`         | **تنظیم نمی‌شود**                                         | پروژهٔ Neon هنوز ساخته نشده (بخش ۹). تا وقتی ست نشود، برنامه روی fallback کار می‌کند — بخش ۷ را حتماً بخوان.                                                       |

⚠️ **هیچ‌وقت** مقدار واقعی `DATABASE_URL` یا شناسهٔ زرین‌پال را در
گیت کامیت نکن، در چت نفرست و در فایل ننویس — فقط در داشبورد ورسل، در
بخش Environment Variables.

## ۷. هشدار مهم: تا وقتی Neon نیست، دیتابیس واقعی نداری

بدون `DATABASE_URL`، برنامه از **seed-JSON + حافظهٔ موقت داخل سرور**
استفاده می‌کند (`src/lib/store.ts`): منو همان ۱۲ نوشیدنیِ فایل seed
است و سفارش/رزرو/خبرنامه فقط تا وقتی سرور ری‌استارت نشده زنده‌اند.

روی ورسل یعنی: **با هر دیپلوی جدید (و هر بار که ورسل سرور را خاموش و
روشن کند)، همهٔ سفارش‌ها و رزروهای ثبت‌شده پاک می‌شوند.** این برای دمو
قابل‌قبول است، ولی دیتابیس پروداکشن نیست — هرگز با مشتری طوری رفتار
نکن که انگار سفارش‌ها ماندگارند، تا وقتی Neon وصل نشده.

## ۸. چرا ریپو عمومی شد — با اینکه مدرک لایسنس هنوز باز است

مدرک لایسنس تمپلیت (فاز ۰) هنوز باز است — هیچ رسید یا فایلی که استفادهٔ
مجدد از عکس‌ها و فونت‌های تمپلیت را پوشش بدهد، تحویل داده نشده. پیشنهاد
اولِ این سند این بود که ریپو Private ساخته شود تا وقتی مدرک برسد؛ اما
الهه صراحتاً انتخاب کرد که ریپو **عمومی بماند** («عمومی بماند، پوش کن»،
۱۴۰۴/۹/۴) و ریپو همان‌طور ساخته شد. این یک تصمیم آگاهانهٔ اوست، نه
فراموشی؛ ولی ریسکش سر جایش است: تا وقتی مدرک لایسنس نرسد، کدِ مشتق از
تمپلیت به‌صورت عمومی در دسترس است. اگر مدرک رسید، چیزی برای تغییر نیست؛
اگر نرسید و خواستی خصوصی‌اش کنی: **Settings → General → Danger Zone →
Change visibility → Private**.

## ۹. اضافه‌کردن Neon بعداً — قدم‌به‌قدم

(خلاصهٔ قدم‌های کامل در `docs/fa/phase-06-backend.md` بخش ۹.)

1. در [neon.tech](https://neon.tech) یک پروژهٔ رایگان بساز (نامش
   مهم نیست، مثلاً `ela-coffee`).
2. از داشبورد Neon، رشتهٔ اتصال Postgres را کپی کن — شکلی شبیه
   `postgres://user:password@host/dbname?sslmode=require`.
3. در داشبورد ورسل: **Settings → Environment Variables → Add New**،
   نام `DATABASE_URL`، مقدار همان رشته، محیط‌ها: Production و Preview
   (و Development اگر لوکال هم می‌خواهی). **Save** را بزن.
4. **Redeploy** کن (Deployments → روی آخرین دیپلوی، منوی `⋯` →
   **Redeploy**) — بدون redeploy، متغیر جدید به سرور نمی‌رسد.
5. مایگریشن را روی Neon اجرا کن (یک‌بار، از ترمینال خودت):
   ```bash
   pnpm --filter web db:migrate
   pnpm --filter web db:seed
   ```
   (با `DATABASE_URL` در `apps/web/.env.local`.)
6. مطمئن شو: یک سفارش آزمایشی ثبت کن و در داشبورد Neon ببین که جدول
   `Order` پر شده. اگر `DATABASE_URL` خالی بماند، برنامه بی‌صدا برمی‌گردد
   به fallback — پس همین چک، تنها راه مطمئن‌شدن است.
7. بعد از وصل‌شدن Neon، یک redeploy دیگر لازم نیست؛ فقط قدم ۵ و ۶.

## ۱۰. Preview در برابر Production

- **Production** (`ela-coffee-yi88.vercel.app`): فقط از پوش به `master`
  ساخته می‌شود. این همان چیزی است که مشتری می‌بیند.
- **Preview** (آدرس تصادفی مثل `ela-coffee-git-<branch>-….vercel.app`):
  از هر پوش به شاخهٔ دیگر یا هر PR ساخته می‌شود. برای تست تغییر قبل
  از مرج است؛ داده‌هایش هم روی همان fallback (یا Neon، اگر ست شده
  باشد) است، پس سفارش آزمایشی روی Preview هم پاک می‌شود.
- **هر redeploy** در ورسل، سرور را از نو می‌سازد؛ اگر Neon وصل نیست،
  داده‌های fallback پاک می‌شوند (بخش ۷).

## ۱۱. خواندن یک ران CI

در ریپوی گیت‌هاب، تب **Actions** → رانِ مربوط به کامیتت را باز کن:

| جاب     | چه می‌کند                                                            | اگر قرمز شد                                                                                                                                                     |
| ------- | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `check` | typecheck، lint، تست واحد، build، و `pnpm audit --audit-level high`  | روی قدم قرمز کلیک کن؛ لاگ دقیقاً می‌گوید کدام تست یا کدام advisory. `pnpm audit` اولین‌بار در CI اجرا می‌شود — در سندباکسِ ساخت، registry جلویش را می‌گرفت (403). |
| `e2e`   | نصب Chromium + Firefox و اجرای `pnpm --filter web test:e2e` (۵۸ تست) | معمولاً تایمینگ/انیمیشن است؛ اول لاگ قدم را بخوان، بعد تست را لوکال با `--headed` اجرا کن.                                                                       |

قانون: **روی کامیت قرمز دیپلوی نکن.** اول قرمزی را درست کن، کامیت
جدید بزن و پوش کن؛ CI دوباره اجرا می‌شود.

## رفع آسیب‌پذیری‌های audit (اولین اجرای CI)

اولین ران CI جاب check را قرمز کرد — نه به‌خاطر کد ما، بلکه چون
`pnpm audit --audit-level high` دو آسیب‌پذیری high پیدا کرد که هر دو
از وابستگی‌های انتقالی Prisma می‌آمدند (`@prisma/config`):

- `deepmerge-ts` ‏7.1.5 — خستگی پشته هنگام ادغام گراف‌های بازگشتی
  (GHSA-ggr8-5vv4-36mx)؛ نسخهٔ اصلاح‌شده ‏≥8.0.0
- `effect` ‏3.21.0 — ‏ReDoS در `Schema.TemplateLiteral`
  (GHSA-7589-6fvf-x4pw)؛ نسخهٔ اصلاح‌شده ‏≥3.22.1

به‌روزرسانی Prisma به آخرین 6.x (‏6.19.3) کافی نبود، چون همان
`@prisma/config` هنوز نسخه‌های آسیب‌پذیر را می‌خواست؛ پس در
`package.json` ریشه دو override گذاشتیم:

```json
"pnpm": {
  "overrides": {
    "deepmerge-ts": "^8.0.0",
    "effect": "^3.22.1"
  }
}
```

بعد از آن lockfile ‏`deepmerge-ts@8.0.2` و `effect@3.22.5` را حل
می‌کند و typecheck/lint/‏224 تست/build همه سبز می‌مانند. هر دو
آسیب‌پذیری در مسیر build-time پریسما بودند، نه در مسیر درخواست‌های
کاربر، ولی دروازهٔ audit برای همین ساخته شده بود — به‌جای غیرفعال‌کردنش
آن‌ها را واقعاً رفع کردیم.
